# V3.0 MVP 功能架构

依据：[product-definition.md](../product-definition.md) 第 3、4、7 章；现状见 [gap-analysis.md](gap-analysis.md)。

## 1. 架构原则

1. **用户触发，AI 执行一次就停。** 除了探索对话的单轮回复，没有任何 AI 任务会自动接着触发下一个 AI 任务。自动循环（生成 → 评审 → 优化 → 再生成）不再是默认路径。
2. **一个事实来源。** 需求基线是唯一的需求数据；Brief 是它的确认快照，PRD 章节通过 ID 引用它。
3. **能用确定性代码做的不用模型。** 聚合、去重、评分、成熟度、影响范围、Stale 标记都是后端代码。
4. **不按定义文档的角色名一一建 Agent。** 定义第 7 章列了 7 个角色；其中 Aggregator 和 Scoring 已经是确定性代码，保持不变。实际调用模型的只有 5 类调用。

## 3. 模块职责、输入与输出

| 模块 | 类型 | 职责 | 输入 | 输出 | 触发 |
|---|---|---|---|---|---|
| Project | 代码 | 项目生命周期、阶段、汇总计数 | 用户操作 | Project 记录 | 用户 |
| Conversation | 代码 | 保存消息和每轮问题状态 | 用户回答、AI 回复 | 消息、问题记录 | 用户提交一轮 |
| **Explorer** | 模型 | 理解本轮回答，抽取条目，生成下一轮 1～3 个问题 | 基线（当前状态）+ 最近 N 轮对话 + 本轮回答 / 跳过 | 本轮理解摘要；新增 / 更新的条目（Inferred / Proposed，带原文片段）；下一轮问题（优先级、目的、目标分组）；是否建议进入方案阶段 | 每次提交一轮 |
| Baseline | 代码 | 条目增删改、状态流转、修改记录、关联 | Explorer 输出、用户编辑 / 确认 / 拒绝 | 条目、修改记录、links | 持续 |
| **Analyst** | 模型 | 主动发现 A 完整性、B 一致性、C 场景、D 风险、E 机会 | 基线（只含非 Rejected 条目）+ 已有的 open / deferred / rejected 发现（用于去重） | Finding（证据引用条目 ID） | 用户点"检查"；进入方案页；生成 Brief 前 |
| Brief | 代码 | 生成基线快照、确认、版本 | 基线 + 用户填写的叙述字段 | Brief 版本（冻结条目 ID 和内容） | 用户 |
| **Generator · 大纲** | 模型 | 生成项目适用的章节结构 | 已确认 Brief | 章节列表（目标、内容、关联条目、依赖、未定信息） | 用户 |
| **Generator · 正文** | 模型 | 逐章生成 Markdown，标注条目 ID 和事实标签 | 大纲中的该章 + 关联条目 + 前序章节标题与摘要 | 章节正文（流式） | 用户确认大纲后，按章依次 |
| **Reviewer ×3** | 模型 | Tech / UX / Biz 独立评审，允许零问题 | 章节（全文或限定范围）+ Brief + 结构检查 + 已有 Finding | 维度分 + Finding | 用户点"审查"；影响检查（限定章节） |
| Aggregator | 代码 | 去重、与项目已有 Finding 匹配、排序、计分 | 三份评审 | 项目级 Finding、文档质量分 | 评审完成 |
| **Optimizer** | 模型 | 只针对用户采纳的 Finding 提出章节修改 | 采纳的 Finding（含用户修改意见）+ 目标章节 + 关联章节 + must_preserve | 每章的修改提案（ADD / UPDATE / REMOVE / CONSOLIDATE / RETAIN + diff） | 用户点"按采纳的问题优化" |
| Impact | 代码 | 判断修改类型、找关联、标 Stale | 章节 diff + links | 受影响章节、Stale Finding | 每次保存章节 |
| Quality | 代码 | 文档质量、需求成熟度、实施就绪度、阻塞项 | 评审分、基线、章节结构、Finding | 四个指标 | 数据变化时重算 |
| Versions / Export | 代码 | 版本快照、对比、恢复查看、Markdown 导出 | 章节 | 版本、diff、.md | 用户 |

### 调用模型的 5 类任务

| 调用 | 结构化输出 | 流式 | 复用 V2.0 |
|---|---|---|---|
| Explorer | 是 | 否（单轮结果较短） | `_validated_structured`、`failures` |
| Analyst | 是 | 否 | Finding 准入规则、`normalize_review` 的证据与置信度处理 |
| Generator（大纲 / 正文） | 大纲是；正文否 | 正文是 | 流式、完成标记、截断不重试、事实规则、篇幅预算 |
| Reviewer ×3 | 是 | 否 | 全部：Rubric、Prompt、去重、复查 |
| Optimizer | 是 | 否 | `OptimizerOutput`、change_type、`build_revision_plan` 的 ID 校验 |

## 4. 去掉或合并的东西

| 定义文档中的角色 / 机制 | 处理 | 理由 |
|---|---|---|
| Requirement Explorer 与 Product Analyst | 保留为两个调用 | 职责和触发频率不同：Explorer 每轮都跑、要快；Analyst 低频、要全面。合并会让每轮对话都做全面分析，成本和噪音都高 |
| Aggregator | 确定性代码 | 已在 V2.0 实现；不需要模型 |
| Scoring | 确定性代码 | 同上；新增指标也是确定性的 |
| 变更类型分类 | 规则 + 现有 Reviewer | 不新增"分类 Agent" |
| 多方案对比 | P1 | MVP 由 Analyst 的机会类 Finding 承载替代方案，不单独建模块 |
| 自动迭代循环 | 降级为可选快捷操作 | 与"只修改用户采纳的问题"冲突 |

## 5. 功能范围

### MVP P0

| 模块 | 功能 | 验收要点 | 说明 |
|---|---|---|---|
| 项目 | 创建、列表、继续、改名、删除（二次确认） | 关闭后重开可恢复；不被 TTL 清理 | 定义 4.2 只要求创建 / 保存 / 继续；改名和删除是长期工作区的基本操作，建议纳入 |
| 输入 | 入口 A 想法、B 粘贴已有需求 | 不丢失用户明确约束 | 入口 C 见下 |
| 探索 | 多轮问答、跳过、不知道、问题目的说明 | 每轮 1～3 问；不重复问已确认信息 | |
| 基线 | 12 分组、6 种状态、来源、编辑、确认、拒绝、修改记录 | 推断不能自动变成已确认 | |
| 探索发现 | Analyst A–E；采纳 / 暂缓 / 拒绝 | 每条有依据（条目 ID） | |
| Brief | 生成、编辑叙述字段、确认、版本 | PRD 只读确认版 | |
| 大纲 | 生成、增删章节、调整顺序 | | |
| 正文 | 逐章流式生成、单章重试 | 单章失败不影响已完成章节 | |
| 编辑 | 按章节编辑 Markdown、保存、人工来源标记 | AI 不覆盖人工章节 | |
| 审查 | Tech / UX / Biz | 支持零问题 | |
| Finding | 采纳、修改后采纳、拒绝、暂缓；Stale；复查结论 | 状态可追踪；被拒绝的问题不重复出现 | |
| 定向优化 | 只改采纳的问题；修改提案需确认 | 不扩大范围 | |
| 版本 | 保存版本、查看历史、对比 | | |
| 影响检查 | 确定性范围 + 按需语义检查 | 历史 Finding 正确更新 | |
| 质量 | 文档质量、需求成熟度、实施就绪度、阻塞项 | 不以单一分数为标准 | |
| 导出 | Markdown | 内容完整，去掉内部锚点语法 | |
| 入口 C | 粘贴已有 PRD → 切章节 → 审查 | | 定义 3.2 列为入口，4.2 未单列。复用度高，建议 P0；若排期紧张可移到 P1 |

### V1 P1

- 产品方案页的多方案对比。
- 完整需求追溯图（MVP 只有章节侧栏的追溯链）。
- 假设验证跟踪（验证方式、负责人、结果）。
- 变更影响可视化。
- 行业与产品类型模板（Q-005）。
- PDF / DOCX 导出；PDF / DOCX 上传解析（Q-004）。
- PRD 转测试用例。
- 人工评审意见管理。
- 深色主题（需独立设计，定义 9.3）。
- 自定义模型 Provider（Q-003）。

### 长期 P2

团队协同、企业知识库、Jira / Linear / 飞书集成、原型与流程生成、PRD 与代码关联、交付后覆盖检查、上线数据回流。

### 暂不开发

自动生成研发代码；复杂企业级权限；多人实时协同；大规模外部知识库；无限模型调用；AI 建议自动加入正式需求；BI 分析平台。另外：**不再开发"全自动多轮迭代直到达标"作为主流程**。

## 7. 成本控制

- 每类调用有单次 token 上限和失败策略，沿用 V2.0 `failures.py`。
- 探索调用只发送基线（压缩为"ID + 分组 + 状态 + 内容"）和最近 3 轮对话；更早的对话由基线代表。
- Analyst、Reviewer、Optimizer 都由用户触发；页面显示"这一步会调用模型"。
- 项目级记录 token 与费用累计（复用 `telemetry.py`）。
