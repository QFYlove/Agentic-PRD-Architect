# 方法论

**Status:** P0 修订稿（v0.2），待人工审核。

## 1. 研究问题与假设

主问题见 [README.md](README.md)。第一阶段要回答的是一个整体比较：

> 完整工作流（多次调用 + 多角色评审 + 修订循环）相对一次性生成，在本 Rubric 下的质量差异，以及为此付出的 Token、耗时和成本。

第一阶段**不能**回答"多角色架构本身是否有独立贡献"。B 比 A 多出大约一个数量级的模型调用，并且会按内部评分从多个版本中挑选最佳版本；任何质量差异都同时混合了"调用次数更多""有修订循环""有多个评审角色""有版本选择"四种因素。把 B 的收益解释为多 Agent 架构的独立贡献，需要第二阶段的对照组（第 3 节）。

## 2. 第一阶段条件

### 条件 A：单 Agent 一次性生成

- 调用 `OpenAICompatibleLLMProvider.stream_prd`，参数为 `iteration=1`、`revision_plan=None`、`baseline_prd=None`，与 B 的 v1 完全相同（同一 system prompt、同一 `<user_input_json>` 包装、同一 `max_tokens`、同一 thinking 设置、同一输出语言判定）。
- 完整性校验与 B 的 Generator 相同：`validate_generated_prd`（`finish_reason` + 结束标记两个独立信号）。
- 重试策略与 B 的 Generator 相同：最多 2 次尝试，单次 240 秒，可重试错误与 B 一致。
- 不调用评审、聚合或优化。

### 条件 B：完整多 Agent 工作流

- 通过 `RunManager` + `AgentWorkflow` 无 HTTP 运行（复用 `backend/tests/helpers.py` 的组装方式），使用内存 RunStore，不触碰 `data/agentic-prd.sqlite3`，不 import `backend.main`。
- 产品默认配置：`quality_threshold=85`、`max_iterations=3`，所有超时保持默认（Generator 240s、Reviewer 45s、Optimizer 60s、整次 run 600s）。

### 派生的待评文档

每个用例产出最多四份待评文档，三份 B 文档始终分别记录、分别评分（内容完全相同时复用同一份评分，但仍按各自标签报告）：

| 文档 | 来源 | 用途 |
|---|---|---|
| `A` | 条件 A 的输出 | 主比较的基线 |
| `B.best` | B 的 `best_version` | **主结果**：产品呈现给用户的版本 |
| `B.last` | B 的最后一个已提交版本 | 次要结果：不经过最佳版本选择时的产出 |
| `B.v1` | B 的第一个版本 | 与 A 同 prompt 的另一次采样；与 `B.best` 对比得到循环内变化 |

三个比较及其含义边界：

1. **`B.best − A`：完整产品策略的效果。** B 相对 A 同时多了：更多次模型调用、多角色评审、修订循环，以及"从最多 3 个版本中按内部评分挑出最佳版本"这一选择步骤。这个差值衡量的是整套产品策略相对一次性生成的效果，**不代表多 Agent 架构的独立因果贡献**。
2. **`B.best − B.v1`：同一次运行内的变化。** 同样包含选择效应：`best_version` 是按产品内部评审分数挑出来的，内部分数上 `B.best ≥ B.v1` 由构造保证，但外部评分不一定如此。因此报告同时给出 `B.last − B.v1`，它不经过选择步骤。
3. **`A − B.v1`：同 prompt 两次采样的差异。** 每个用例只有一对样本，**只能作为随机波动的初步参考，不能可靠估计随机方差**；8 个用例的差值分布也混合了用例本身的难度差异。若该差值与第 1 项量级相当，只能说明 Pilot 无法区分效应与噪声，需要按第 11 节扩大规模，而不能据此推断方差大小。

## 4. 模型

- Pilot 的 A、B 两个条件以及 B 内所有节点使用同一模型：DeepSeek 官方 API 的 `deepseek-flash`，base URL `https://api.deepseek.com`。
- **`deepseek-flash` 是浮动别名。** DeepSeek 不提供带日期的固定版本 ID；别名背后的快照可能在实验期间被服务商升级（例如 2026-10-17 的 V4.1-Flash-1017 更新就沿用了同一 ID）。因此：
  - 每一次调用都必须记录服务端响应中的原始 `model` 字段（`response.model`，流式调用取 chunk 的 `model`），见 [experiment-protocol.md](experiment-protocol.md) 第 5 节。
  - 每个批次开始时记录 DeepSeek 官方更新日志的最新条目日期，作为"当时别名指向哪个快照"的旁证。
  - 若同一批次内出现不同的 `response.model` 值，该批次标记为 `model_drift`，不与其他批次合并分析。
  - `response.model` 只是服务端自报的标识，可能只返回别名本身，不一定能区分快照。报告中如实写明这一点，不把它当作快照已被核实的证据。
- thinking 模式由产品硬编码为 `disabled`（`backend/main.py:145`），A 和 B 一致。
- 温度、top_p、seed 均不发送（产品代码不支持），两个条件都使用服务端默认值。这意味着输出不可复现，只能用重复运行估计波动。
- Judge 模型尚未确定（见 [rubric.md](rubric.md) 第 8 节），建议不使用 DeepSeek 家族，以减少自我偏好偏差。

## 5. 变量控制

| 可控（A、B 一致） | 无法完全控制 |
|---|---|
| 冻结的输入字段（`user_idea`、`target_audience`、`user_constraints`） | 服务端采样随机性（无温度、seed） |
| 模型 ID、base URL、`max_tokens=16000`、thinking 关闭 | 浮动别名背后的快照 |
| Generator system prompt、composition rules、结束标记校验 | 服务端负载、网络延迟、限流 |
| 输出语言（全部用例为中文，输入含 ≥4 个 CJK 字符 → `zh`） | 上下文缓存命中（B 重复发送相同 system prompt，更容易命中，实际成本低于按价目表估算） |
| 重试策略、单次超时 | 峰谷定价（同一 Token 在不同时段价格不同） |
| 运行环境、代码 commit、依赖版本 | Judge 自身的偏差与波动 |
| 用例内 A/B 运行顺序随机并记录，同一用例的 A、B 在同一时段内完成 | 盲评的残余泄露（B 的文本可能明显更长、更完善） |

## 6. 用例与金标准

- 8 个原创模拟用例，覆盖 8 种需求类型，见 [cases/](cases/)。不包含任何公司内部资料。
- 只有 `frozen_input` 下的三个字段会发送给模型，且两个条件完全相同。其余字段（金标准、评测说明）对被测系统不可见。
- 字段长度满足产品 API 限制：`user_idea` 10–5000 字符、`target_audience` ≤1000、`user_constraints` ≤2000。
- 金标准分四类条目：
  - `hard_constraints`（H）：题面中明确、可核对的约束，每条附逐字引用，引用不在冻结输入中的用例无法加载。只有违反 H 条目的矛盾才算"违反硬约束"。有意保留的歧义、推导项、事实数据、冲突的任一侧都不收录为 H 条目。
  - `rule_relations`（P07）：规则之间的关系，分为 `explicit`（题面原文）、`derived`（推导，不是硬约束）、`design_choice`（多种可接受方案）。
  - `conflicts`（P06）：互相冲突的要求；明确取舍其中一侧不算违反约束。
  - `required_items`（R）：PRD 必须覆盖的原子需求，计入"需求覆盖率"。
  - `clarifications`（C）：PRD 必须提出或明确标注为待确认的问题，计入"正确性与假设管理"。
  - `critical_defects`：用例专属的严重缺陷条件，与通用条件共同构成严重缺陷门槛。
- 每个核心条目（`core: true`）都写明 `impact`：缺失后造成的实际影响。说不出实际影响、只是设计偏好的条目一律为普通项。
- 每个 R 条目标注来源：`E` 表示题面明确要求；`D` 表示题面未明说、但专业 PRD 必须定义；`ED` 表示题面给出了一部分（如数值），其余部分（如达到上限后的行为）需要推导。`D` 和 `ED` 条目必须附 `rationale`，它们最容易引入评测者偏好，冻结前需要第二人逐条复核。
- 核心条目（`core: true`）权重为 2，其他为 1。
- 题面中的歧义如果是有意保留的，必须同时出现在 `clarifications` 中，并在 `judge_notes` 说明哪些处理方式可接受；金标准不得把有歧义的题面当成只有一种正确答案。
- 冻结：人工复核通过后，`cases/manifest.yaml` 记录每个文件的 SHA-256 和冻结 commit。冻结后不再修改；如需修改，新建版本号并在报告中说明，旧版本结果不重算、不混用。

## 7. 评分概述

百分制六维度（需求覆盖率 25、正确性与假设管理 20、业务流程与规则 20、异常处理 15、验收标准与可测试性 15、内部一致性 5）。需求覆盖率按条目连续计分，其余维度为 0–4 锚点，总分为连续值；另设独立的严重缺陷门槛：只有违反明确 H 条目会自动生成候选，候选经人工确认后才应用正确性 1 分封顶，未裁定的文档标记为待定。完整规则见 [rubric.md](rubric.md)。

评分标准独立编写，不复用产品评审 prompt 中的 `SCORING_ANCHORS` 或 `SEVERITY_RUBRIC`（`backend/prompts.py:13-60`），否则 B 等于提前知道考题。金标准对 A、B 都不可见。

## 8. 度量口径

只记录实际测得的值；缺失的度量写 `null`，不估算、不插补。

| 指标 | 口径 | 来源 |
|---|---|---|
| 质量分、维度分 | 见 rubric；分别报告 `auto` 与 `human_reviewed` | 评分产物 |
| 需求覆盖率 | 加权覆盖比例 r（连续值），与覆盖率锚点并列报告 | 程序计算 |
| 严重缺陷率 | 含至少一条**经人工确认**的严重缺陷的文档比例 | 人工 |
| 端到端耗时 | A：从首次请求发出到校验通过（含重试）；B：快照 `elapsed_seconds`（不含暂停，Benchmark 不暂停），并以调用记录的首尾时间交叉核对 | 调用记录、快照 |
| 首 token 延迟 | 每次流式生成调用 | 调用记录 |
| 输入 / 输出 Token | 逐次调用求和，**包含失败尝试和修复调用** | 调用记录（主）、快照 `total_tokens`（交叉核对） |
| 缓存命中 Token | 若服务端响应提供则记录，否则 `null` | 调用记录 |
| 调用次数、重试次数、修复次数 | 按节点统计 | 调用记录 |
| 成本 | 两个口径：①按冻结的价目表快照（含日期、时段规则）估算；②批次结束后与账单对账。只有②可称"可核实成本" | 价目表、账单 |
| 失败率 | 运行最终状态为失败的比例，按错误码分类 | 快照 `error`、调用记录 |
| 质量门槛通过率 | 仅 B：最终状态 `COMPLETED` 的比例 | 快照 |

## 9. 已知度量缺口（基于代码核查）

产品现有记录不足以直接支撑上述指标。以下缺口已确认，Benchmark 的处理方式不修改任何核心代码：

| 缺口 | 位置 | 处理 |
|---|---|---|
| 服务端返回的 `model` 被丢弃，快照只存配置的 model_id | `backend/providers/compatible.py:223,228,286` 读取后未持久化 | 见下一行 |
| Provider 层的 `model` 字段在响应缺失时回落为配置值 `self.model`，无法区分"服务端返回了别名"和"服务端没返回" | `compatible.py:223,228,286` 的 `_field(..., self.model)` | 必须在 SDK client 层截获原始响应。`OpenAICompatibleLLMProvider.__init__` 接受 `client` 参数（`compatible.py:61,68`），Benchmark 注入一个包装 `AsyncOpenAI` 的记录型 client 即可，无需改核心代码 |
| 缓存命中、推理 Token 不解析 | `compatible.py:113-128` | 由记录型 client 从原始 `usage` 读取；字段不存在则记 `null` |
| Reviewer / Optimizer 的重试与修复在快照中不可区分，失败尝试的 Token 丢失 | `backend/workflow.py:577-620`，`attempt` 恒为 1 | 记录型 client 记录每一次 HTTP 调用 |
| 只保留最终错误，没有每次尝试的错误码 | 快照 `error` | 记录型 client 记录每次调用的状态码和异常类别 |
| 成本估算只用单一单价，不区分缓存命中价和峰谷价 | `backend/telemetry.py:20-46` | 不使用产品内的 `estimated_cost_usd` 作为结论；按第 8 节两个口径处理 |
| `TokenUsage` 要求 `total == input + output`，若服务端 total 含其他 Token 会被判为结构化输出无效 | `backend/schemas.py:277-282` | Pilot 中观察；若发生，记为产品缺陷，计入失败率，不在 Benchmark 侧绕过 |

## 10. 冻结与结果规则

沿用 `benchmark/` 的冻结结果规则：

- 不选择性重跑；重跑只能按 [experiment-protocol.md](experiment-protocol.md) 第 7 节预先声明的条件进行，且对 A、B 对称适用、全部记录。
- 结果出来后不修改用例、金标准或 Rubric；如需修改，作为新版本另行运行。
- 原始输出、调用记录、Judge 输出按原样保存，不编辑。
- 评审意见不回灌给任何条件。
- 扩展运行单独标注，不改变已冻结批次的结论。

## 11. 统计与结论边界

- 第一阶段：8 个用例，每个用例每个条件运行 1 次。**只做描述性统计**：逐用例配对差值、差值的中位数与范围、方向计数（B 好 / 持平 / A 好）、各维度均值。
- 不报告 p 值、置信区间或"显著"等措辞，也不做任何显著性宣称。n=8 且每格只有一次运行，没有估计抽样误差的依据。
- "持平"的界限在报告前固定为总分差绝对值 < 2 分，仅用于方向计数，不代表统计意义上的等价。
- 连续分数是主要结果；暂定合格率（rubric 第 6.4 节）只作辅助描述，不能单独支撑质量结论。
- 正式实验规模根据 Pilot 结果决定：若 `A − B.v1` 的差异与 `B.best − A` 量级相当，优先增加用例数（目标 20–30 个），其次每用例重复 3 次；具体方案与统计方法提交审批后再执行。
- 任何结论都必须同时给出成本侧数字（Token 倍数、耗时倍数），并重申第 1 节和第 2 节的归因边界。
