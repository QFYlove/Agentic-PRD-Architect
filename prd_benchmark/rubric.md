# 评分 Rubric

**Status:** P2 修订稿，待人工审核。版本 `rubric-v0.4`。

v0.4 相对 v0.3 的变化：
- 违反 H 条目改为附在条目上的**硬约束主张**，与条目自身判定分开；`contradiction_kind` 只剩 `general` 和 `internal`（2.3 节）。
- 有待定主张时不给出最终总分，只给出基础评分、确认后、否决后三个情景（4.2 节）。人工否决只移除该主张造成的处罚，条目恢复自身判定。
- 一般性矛盾必须给出 `rule_basis`；依附于主张、没有独立证据的一般性矛盾不计入（2.3 节）。
- `behavior_impact` 必须用「」逐字引用文档，并写出具体差异；`defect_key` 改为必填（2.3 节）。
- 正式 Judge Prompt 见 `prompts/system-prompt.md`（`judge-prompt-v0.1`），由 `judge_prompt.py` 组装。

v0.3 相对 v0.2 的变化：
- 矛盾必须有实质影响：每个 `contradicted` 判定都要写明 `behavior_impact`（会导致什么不同的业务行为或实现），纯措辞差异不算矛盾（2.3 节）。
- 新增 `internal` 矛盾类别：文档自相矛盾记入一致性维度，不触发正确性封顶，也不等同于违反硬约束（2.3 节）。
- 同一底层缺陷在正确性维度只计一次（`defect_key`，4.2 节）。
- 违反硬约束的 1 分封顶只在人工确认后生效；候选未裁定时文档状态为 `pending`，同时报告"若确认"的总分；人工否决后重新计算（4.2、6.3 节）。
- 只有 `explicit` 的 H 条目可以支撑硬约束违规；`derived` 关系不能作为 `violated_constraint`（2.3 节）。
- Judge 提出的候选与自动候选引用同一段原文时合并为一条，保留用例专属规则 ID（6.2 节）。
- 明确区分 C 条目的 `missing` 与 `contradicted`（2.2 节）。

v0.2 相对 v0.1 的变化：
- 正确性维度的封顶规则拆成三类问题分别处理：遗漏核心澄清项、一般性矛盾、违反明确硬约束（第 4.2 节）。
- 只有违反明确硬约束会自动进入严重缺陷候选；其余候选必须由 Judge 或人工逐条提出并附证据，所有候选仍需人工确认（第 6 节）。
- 需求覆盖率改为连续计分，总分保持连续；70 分门槛降为辅助指标，不作为质量结论的依据（第 3、6.4 节）。

## 1. 原则

1. **评内容，不评篇幅。** 只判断题面要求的规则是否存在、是否正确、是否可执行。超出需求范围的内容不加分；没有依据而新增的需求按"范围蔓延"在正确性维度扣分。
2. **不评格式和文风。** 表格、Mermaid 图、标题层级、Given/When/Then 写法都不计分；同一条规则写成段落或表格得分相同。
3. **以证据为准。** 每个判定都必须能指向文档中的原文。找不到原文支持的判定无效。
4. **总分由程序计算。** 任何 Judge 都不输出总分，也不采用任何模型自报的总分。
5. **严重缺陷独立于分数。** 严重缺陷不从总分中扣除，而是单独报告。
6. **连续分数是主要结果。** 质量比较以连续的总分、维度分和覆盖率为准；任何阈值（包括 70 分）只是辅助描述。
7. **自动评分不是真值。** 未经人工审核的分数标记为 `auto`。

## 2. 评分单元

| 单元 | 来源 | 计入 |
|---|---|---|
| R 条目 | 用例 `required_items` | 需求覆盖率（第 4.1 节） |
| C 条目 | 用例 `clarifications` | 正确性与假设管理（第 4.2 节）的上限约束 |
| H 条目 | 用例 `hard_constraints` | 判定矛盾是否属于"违反明确硬约束" |
| 规则关系 | 用例 `rule_relations`（目前仅 P07） | 解释判定理由；不单独计分 |
| 冲突 | 用例 `conflicts`（目前仅 P06） | 说明哪些要求互相冲突；冲突任一侧都不是 H 条目 |
| 维度锚点 | 整份文档 | 维度 4.2–4.6 各 0–4 |
| 严重缺陷 | 通用条件 G1–G5 + 用例 `critical_defects` | 第 6 节 |

每个用例的 `hard_constraints` 只收录题面中明确、可核对的约束（数值、比较符、禁止事项、明确的非目标），每条都带 `quote`，必须逐字出现在冻结输入中，否则用例无法加载。以下内容不收录为 H 条目，也不能据此判"违反硬约束"：
- 题面有意保留的歧义（如 P04 恰好 24 小时、快递时间基准，P08 的 4 周是否包含观察期）；
- 推导项（D/ED），包括"授权"表述推出的"只能"（如 P07 用人经理的部门范围）；
- 事实数据（如 P08 的基线数值），引用错误按一般性矛盾处理；
- 冲突的任何一侧（如 P06 的名额固定与离线即时成功、候补递补截止时间）。

部分 H 条目带 `note`，说明该约束的边界（例如 P04-H6 只授予取货前取消的能力，不规定取货后能否取消）。

P07 的 `rule_relations` 分三类：
- `explicit`：题面原文，可引用 H 条目；
- `derived`：由明确规则推导，只用于说明判定理由，**不是硬约束**，不能作为 `violated_constraint`；
- `design_choice`：题面未规定，列出的方案以及其他写明的合理方案都可接受，不得判 `contradicted`。

### 2.1 R 条目判定

| 判定 | 含义 | 计分 s |
|---|---|---|
| `covered` | 文档明确定义了该条目，且内容与题面一致 | 1 |
| `partial` | 提到了但缺少关键要素（例如只说"支持重试"，没有重试条件），或只覆盖了条目的一部分 | 0.5 |
| `missing` | 没有提到 | 0 |
| `contradicted` | 写了，但与题面存在实质冲突 | 0（`internal` 类为 0.5），并按 2.3 节分类 |

条目的 `check` 字段给出判定参考。语义等价即可，不要求关键词一致：同一规则换一种说法、写成表格或段落、使用不同的状态名，都不是矛盾。核心条目（`core: true`）都附有 `impact`，说明缺失后的实际影响；没有实际影响、只是设计偏好的条目一律为普通项。

### 2.2 C 条目判定

C 条目检查的是"关键问题是否被识别"，**不看问题数量**。

| 判定 | 含义 |
|---|---|
| `covered` | 以下任一：①作为待澄清问题明确提出；②做出明确标注为"假设""待确认"的设定 |
| `partial` | 提到相关方向但不具体（例如只说"集成细节待确认"，没有指出要确认什么）；或做了设定并给出理由，但没有标注为待确认 |
| `missing` | 没有提到这个问题；或在正文中采用了某个设定，但既没有标注为假设，也没有把它表述为已确认的事实或决定（只是顺带写进了设计） |
| `contradicted` | 把需要澄清的内容**明确表述为已确认的事实或既定决定**（例如"经确认，AI 回复将自动发送给客户""法规要求 30 日内处理"），并据此做出设计；必须写明 `behavior_impact` |

`missing` 与 `contradicted` 的分界：未标注的假设是遗漏（`missing`）；以确定口吻声称某个未知项已经确定、并让设计依赖它，才是矛盾（`contradicted`）。判断依据是原文的措辞（"假设""暂定""建议"与"已确认""要求""必须"），由 Judge 在引用中给出。

额外提出的、不在清单内的问题既不加分也不扣分；数量只作为协变量记录。泛泛的问题（如"需求是否还有变化"）不能覆盖任何 C 条目。

### 2.3 矛盾的分类

`contradicted` 只用于**实质语义冲突**：文档的规定与题面（或文档自身另一处）不同，并且会导致不同的业务行为或实现。每个 `contradicted` 判定都必须给出 `behavior_impact`，写明哪种行为或实现会因此不同；写不出的，不是矛盾。以下情况不算矛盾：
- 纯措辞差异、同义改写、术语或状态名不同；
- 比题面更细的补充（只要不改变题面规则）；
- 对 `design_choice` 关系、可接受假设、用例 `conflicts` 中任一侧做出的明确取舍；
- 对推导项（D/ED）采用了与 `check` 示例不同、但同样满足条目要求的方案。

每个 `contradicted` 判定归入以下两类之一，并附 `behavior_impact` 与 `defect_key`：

| 类别 | 条件 | Judge 必须给出 | 计入 |
|---|---|---|---|
| `general` | 与题面或某条非 H 规则有实质冲突：违反推导项本身的要求、引用事实数据错误（如 P08 基线）、把待澄清内容写成已确认事实（C 条目矛盾） | `rule_basis`：所依据的 R/C 条目或 `explicit`/`derived` 类 L 关系 | 正确性封顶② |
| `internal` | 文档对该条目自相矛盾（例如两处给出不同的阈值），无法确定应如何实现 | — | 一致性维度（4.6）；该条目按 0.5 计入覆盖率；可由 Judge 另行提出 G5 候选。**不触发正确性封顶，也不等同于违反硬约束** |

`rule_basis` 不能是 H 条目（H 违规走下面的硬约束主张）、`design_choice` 类 L 关系或冲突 K（它们没有唯一正确答案）；程序校验不通过的矛盾记为"未核实"。

**硬约束主张（`hard_constraint_claim`）：** 违反 H 条目原文（例如把 ≥ 写成 >、把"不得自动通过"写成超时自动通过、保留期限数值错误）不是一种矛盾类别，而是附在条目判定上的一条独立主张，包含 `violated_constraint`（H 条目 ID）、逐字引用、`behavior_impact` 和 `defect_key`。附带主张时，条目的 `verdict` 写的是**不考虑该主张时**这一条目本身的判定，也就是人工否决主张后应当保留的判定。

- 程序只接受 `violated_constraint` 是本用例 H 条目 ID、引用逐字存在、`behavior_impact` 通过下文校验的主张；L 关系（包括 `explicit`、`derived`）、冲突 K、R/C 条目或不存在的 ID 一律拒绝，记入"被拒绝的主张"并转人工。
- 如果文档对某条规则既写了与题面一致的版本、又写了违反 H 条目的版本，判 `internal`，不附主张；只有当违反 H 的版本是唯一的、或明确作为最终规则的表述时，才附主张。

**`behavior_impact` 校验（程序）：** 必须用「」逐字引用文档中造成差异的原文，并用至少 8 个字说明具体差异。没有「」引用、引用不在文档中、或说明只是"与题面不一致""存在矛盾"等泛泛措辞的，判定记为"未核实"（矛盾）或主张被拒绝。程序只能检查形式；说明是否真实合理，由人工复核兜底。

**同一底层缺陷：** 同一个底层缺陷可能同时让多个 R、C 条目判为矛盾，或在两轮评审中被重复发现。Judge 必须给这些判定填写相同的 `defect_key`（短横线小写英文串），不同缺陷使用不同的键。程序在正确性维度按 `defect_key` 去重计数；同一 H 条目、同一 `defect_key` 的主张在两轮评审中合并为同一个候选。覆盖率仍逐条计分（rubric 4.7 的跨维度影响是有意设计）。

**依附于主张的一般性矛盾：** 一个 `general` 矛盾如果落在带主张的条目上，或与某条主张共用 `defect_key`，只有在它有**独立的证据**（至少一段主张没有使用的引用）时才计入；否则它只是在复述 H 违规，记为"未核实"（`depends_on_hard_claim`），不得分也不扣分。其规则依据已由上文保证不是 H。

## 3. 计分公式

```
需求覆盖率得分 = 25 × r                         （连续值）
其他维度得分   = 维度权重 × 锚点 / 4            （锚点取两次 Judge 的平均，可为小数）
总分           = 六个维度得分之和（0–100，连续值）
```

加权覆盖率 `r = Σ(w × s) / Σ w`，核心条目 w=2，其他 w=1。

报告同时给出：总分、六个维度得分、r、核心条目覆盖率、C 条目覆盖率，以及第 4.1 节的描述性档位。比较 A、B 时以连续值为准。

## 4. 维度与锚点

维度 4.2–4.6 由 Judge 给出锚点，取满足条件的最高锚点。

### 4.1 需求覆盖率（25 分）——程序根据 R 条目判定计算

得分为 `25 × r`。下表只用于描述，不参与计分：

| 档位 | 条件 |
|---|---|
| 高 | r ≥ 0.90，且所有核心 R 条目为 `covered` |
| 较高 | r ≥ 0.75，且没有核心 R 条目为 `missing` 或 `contradicted` |
| 中 | r ≥ 0.55 |
| 低 | r ≥ 0.30 |
| 很低 | r < 0.30 |

### 4.2 正确性与假设管理（20 分）

| 锚点 | 条件 |
|---|---|
| 4 | 没有与题面矛盾的陈述；超出题面的关键设定都标注为假设或待确认；所有核心 C 条目为 `covered` |
| 3 | 至多 1 处不涉及 H 条目的一般性矛盾；或 1 个核心 C 条目未覆盖；或少量非核心设定未标注假设 |
| 2 | 多处一般性矛盾；或 ≥2 个核心 C 条目未覆盖；或较多关键设定未标注假设就写成既定事实；或存在明显的范围蔓延 |
| 1 | 违反至少一个 H 条目（经人工确认）；或编造关键事实、数值并当作既定事实 |
| 0 | 大面积偏离题面，或答非所问 |

程序按三类问题分别施加上限，最终锚点取 Judge 锚点与各上限中的最小值。三类问题彼此独立计数，同一判定只归入一类；`internal` 矛盾不属于任何一类：

| 类别 | 计数来源 | 上限 |
|---|---|---|
| ① 遗漏核心澄清项 | 核心 C 条目判定为 `missing`（`partial` 不计入） | 1 个 → 3；≥2 个 → 2 |
| ② 一般性矛盾 | 已核实的 `general` 类矛盾，按 `defect_key` 去重；与已确认主张同键的不再重复计入 | 1 处 → 3；≥2 处 → 2 |
| ③ 违反明确硬约束 | **经人工确认**的硬约束主张，按候选去重 | ≥1 处 → 1 |

**按情景计分。** 每份文档按以下情景分别计算（每个情景都对两轮评审分别计算后取平均）：

| 情景 | 应用的主张 | 说明 |
|---|---|---|
| `base` 基础评分 | 不应用任何主张 | 条目自身判定下的分数 |
| `if_confirmed` 确认 H 违规后 | 已确认 + 全部待定 | 展示待定主张全部成立时的下限 |
| `if_rejected` 否决 H 违规后 | 仅已确认 | 展示待定主张全部不成立时的分数 |
| `final` 最终总分 | 仅已确认 | **只在没有待定主张时给出**；有待定主张时为空 |

应用一条主张的效果只有两项：该条目在覆盖率中按 0 计；③计入一处。否决一条主张就是不应用它，条目恢复自身判定，其余判定不受影响。每条待定主张单独确认时的总分另行列出（`candidate_effects`），便于人工逐条裁定。

遗漏不等于错误：①只说明文档没有识别某个关键未知项，最低只封顶到 2；②是写错了但没有触碰题面的硬约束；只有经确认的③会把正确性压到 1 分。

只有通过引用校验（第 8 节）的判定才计入上述计数；引用校验失败的判定不触发上限，转人工。

### 4.3 业务流程与规则（20 分）

| 锚点 | 条件 |
|---|---|
| 4 | 主流程和关键分支端到端闭环；每条规则写明触发条件、执行者和结果；边界值明确（包括 `≥` 与 `>` 的区别）；涉及的角色、状态没有遗漏 |
| 3 | 闭环，但有 1–2 处次要分支或边界未定义，工程师可以合理推断，不会导致实现分歧 |
| 2 | 存在会导致实现分歧的缺口：某个关键分支未定义，或角色职责不清 |
| 1 | 主流程断裂，或关键业务规则缺失 |
| 0 | 没有可执行的流程描述 |

### 4.4 异常处理（15 分）

"处理语义"是指：系统行为 + 用户可见结果 + 数据或状态的去向。只列出异常名称而不给处理语义的，最高 1 分。

| 锚点 | 条件 |
|---|---|
| 4 | 题面明示或必然隐含的异常（失败、超时、取消、并发冲突、权限拒绝、数据缺失、外部依赖不可用等）都给出处理语义 |
| 3 | 缺 1 类非核心异常，或某类异常只有系统行为没有状态去向 |
| 2 | 只覆盖常见异常；题面明示的异常中有 1 类缺失 |
| 1 | 只泛泛提及"异常需要处理"，或只列名称 |
| 0 | 没有异常处理内容 |

### 4.5 验收标准与可测试性（15 分）

"可判定"是指：写明了前置条件或输入、操作、期望结果，或可量化的阈值，测试人员不需要追问就能写出用例。

| 锚点 | 条件 |
|---|---|
| 4 | 每个核心 R 条目都有可判定的验收条件 |
| 3 | ≥75% 的核心 R 条目有可判定的验收条件 |
| 2 | 50%–75% |
| 1 | <50%，或验收条件以"体验良好""快速响应"等不可判定的措辞为主 |
| 0 | 没有验收标准 |

### 4.6 内部一致性（5 分）

`internal` 类矛盾（2.3 节）的证据记入本维度。

| 锚点 | 条件 |
|---|---|
| 4 | 数值、状态名、角色权限、术语前后一致 |
| 3 | 1 处不影响实现的不一致（如同一状态两种叫法） |
| 2 | 1 处规则冲突（两处对同一规则给出不同数值或行为） |
| 1 | 多处规则冲突 |
| 0 | 核心规则自相矛盾 |

### 4.7 维度重叠说明

同一缺口可能同时影响覆盖率与其他维度（例如缺少超时处理既是 R 条目缺失，也拉低异常处理）。这是有意的：覆盖率衡量"清单上的条目是否在"，其他维度衡量"整份文档的质量"。为避免重复计罚被放大，Judge 在其他维度只能引用该维度自己的证据，不得以"覆盖率已扣分"为由加重或减轻。

## 5. 长度与格式偏差控制

- Judge 指令中明确：篇幅、表格、图、章节数量都不是得分依据；超出题面的内容不加分。
- 程序记录每份文档的字符数、标题数、表格数、Mermaid 块数，作为协变量，不计分。
- 报告中给出总分与字符数的相关性，并按长度三分位分层展示结果。若 B 的优势只在长文档层出现，需在结论中说明。
- 覆盖率以 R 条目为单位逐条判定，而不是整体印象打分，以减少"写得多就显得全"的偏差。

## 6. 严重缺陷门槛

### 6.1 通用严重缺陷

| ID | 条件 |
|---|---|
| G1 | 违反题面的明确硬约束（H 条目）：数值、比较符、禁止事项、明确的非目标被纳入首期 |
| G2 | 把核心 C 条目当作已确认事实写入，并据此做出核心设计 |
| G3 | 权限、隐私、资金相关的规则存在不安全的设计（越权可见、未授权扣款或退款、绕过审批） |
| G4 | 状态机中存在没有出口的非终态，或允许题面明确禁止的状态转换 |
| G5 | 核心规则自相矛盾，导致无法确定应如何实现 |

### 6.2 用例专属严重缺陷

见各用例的 `critical_defects`。

**候选合并规则（只有以下三条，程序不做其他合并）：**
1. 硬约束主张：H 编号和 `defect_key` **都相同**才合并（跨条目、跨轮次）。同 H 不同 `defect_key`、不同 H 同 `defect_key` 都保持独立。
2. Judge 逐条提出的候选：规则 ID 和引用**都相同**才合并（跨轮次）。
3. Judge 提出的用例专属候选（或 G1）与某条主张引用同一段原文（空白差异不计）时，并入该主张，规则 ID 改为用例专属 ID，原 ID 记入 `merged_rule_ids`；人工对任一 ID 的裁定都作用于合并后的候选。但以下情况**不并入**：G2–G5（它们是不同的严重缺陷条件）；引用同时命中多条主张；同一条主张上有两个不同的用例专属规则；引用未通过校验。

程序判断不了的情况只标记、不处理，在报告的候选表中以"人工复核提示"列出：同一候选在不同位置出现时没有任何共同引用（Judge 可能把同一个 `defect_key` 用在了两个缺陷上）；同 H 不同 `defect_key` 的主张引用了同一段原文（可能是同一缺陷被命名了两次）；引用命中主张但按上条规则不并入。人工可以据此在裁定中只确认其中一条，或在 `item_overrides` 中改判。

**冲突用例（P06）：** 只要文档明确识别了 `conflicts` 中的冲突、解释取舍、标明被放弃的要求并提出决策建议，就不能因为没有同时实现冲突双方而生成严重缺陷候选。P06 的严重缺陷只针对"未说明冲突就声称双方都满足"或"完全忽略某一方"的情形。

### 6.3 候选的来源与判定流程

严重缺陷候选只有两个来源：

1. **自动生成：** 只有通过校验的硬约束主张（2.3 节）才由程序自动生成候选（规则 ID 记为 `G1`，附 `violated_constraint`；同一 H 条目、同一 `defect_key` 合并为一个候选）。`derived` 规则关系、遗漏核心澄清项、一般性矛盾、`internal` 矛盾、`partial` 或 `missing` 判定，**不会**自动生成候选。
2. **逐条提出：** Judge 或人工可以针对 G2–G5 或用例专属条件提出候选，每条必须附规则 ID、原文引用和理由。没有通过引用校验的候选标记为"引用未核实"，仍进入人工复核，但不计入任何统计。

所有候选都必须由人工确认或否决：
- 只有人工确认的候选才计入严重缺陷率；
- G1 候选的确认与否决会改变分数，程序在每次生成报告时按最新裁定重新计算（4.2 节）；只要还有未裁定的 G1 候选，文档就没有最终总分；
- Judge 逐条提出的候选（G2–G5、用例专属）只影响严重缺陷率，不改变分数；
- 只要还有任何未裁定的候选，文档状态就是 `pending`，暂定合格记为"待定"；
- 人工裁定引用了不存在的候选 ID 时，程序忽略该裁定并在报告中列出。

人工也可以补充 Judge 漏掉的严重缺陷，需写明规则 ID 与引用；人工补充的候选直接视为已确认。

### 6.4 辅助指标：暂定合格率

暂定合格状态 `pass_status` 与数值评分分开计算：
- `pending`：存在任何未裁定的候选（G1 主张、G2–G5、用例专属候选），或者因 G1 主张未裁定而没有最终总分。即使数值上已有最终总分且 ≥ 70，也不显示为合格；
- `fail`：没有未裁定候选，且有经人工确认的严重缺陷，或最终总分 < 70；
- `pass`：没有未裁定候选，没有确认的严重缺陷，且最终总分 ≥ 70；
- `unscored`：没有有效的 Judge 输出。

G2–G5 和用例专属候选只影响合格状态和严重缺陷率，不改变数值评分；只有 G1 主张会改变数值评分。

这只是辅助描述：
- 质量比较以连续总分、维度分和覆盖率为准，不得仅凭合格率得出质量结论；
- 70 分没有经过校准，不是经过验证的通用质量标准。Pilot 后根据人工对"这份 PRD 能否交给研发"的整体判断再校准，新阈值只在下一个 Rubric 版本生效，不回溯修改本批次。

## 7. 职责划分

| 负责方 | 内容 | 不负责 |
|---|---|---|
| 程序 | 完整性信号（结束标记、`finish_reason`）；长度与结构协变量；匿名化；Judge 输出的解析与格式校验；**引用原文逐字存在性校验**；`behavior_impact` 形式校验；`rule_basis` 与 `violated_constraint` 有效性校验；r、上限约束、情景总分计算；硬约束主张的候选生成；严重缺陷汇总；Judge 一致率；Token、耗时、成本统计；哈希校验 | 任何语义判断（不做关键词计分） |
| LLM Judge | R、C 条目逐条判定与引用；矛盾的类别、`rule_basis`、`defect_key`；硬约束主张；维度 4.2–4.6 的锚点、证据与缺陷列表；G2–G5 与用例专属候选 | 总分；严重缺陷的最终确认；需求覆盖率得分（由程序从 R 判定计算） |
| 人工 | 用例与金标准的冻结前复核；Judge 校准；复核范围见第 9 节；严重缺陷最终确认；争议裁定；阈值校准 | — |

## 8. LLM Judge 输出要求

**模型：** 待人工决定。建议使用非 DeepSeek 家族的模型，以降低自我偏好偏差（B 的三个评审者也是 `deepseek-flash`，同家族 Judge 可能偏好 B 已按其口味优化过的文本）。若预算允许，使用两个不同家族的 Judge 交叉评分。目前只有 Mock Judge 和正式 Prompt（`prompts/system-prompt.md`），没有接入任何真实 Judge；接入需另行批准，Prompt 也尚未经过真实模型校准。

**输入：** 匿名文档正文、该用例的冻结输入、H/R/C 条目清单（含 `check`、H 的 `note`）、`rule_relations` 与 `conflicts`（如有）、用例与通用严重缺陷条件、本 Rubric 第 1–6 节。不提供条件标签、Token、耗时或其他文档。

**输出：** 单个 JSON 对象，结构由 `prd_benchmark/judge.py` 中的 `JudgeOutput` 固化：

```json
{
  "judge_id": "...",
  "items": [
    {"item_id": "R1", "verdict": "covered|partial|missing|contradicted",
     "evidence_quotes": ["文档原文片段"], "rationale": "判定理由",
     "contradiction_kind": "general|internal|null",
     "behavior_impact": "「文档原文」会导致什么不同的业务行为或实现|null",
     "defect_key": "same-underlying-defect|null",
     "rule_basis": ["R3", "L8"],
     "hard_constraint_claim": {"violated_constraint": "H2", "quotes": ["..."],
       "behavior_impact": "「...」...", "defect_key": "..."} }
  ],
  "clarifications": [
    {"item_id": "C1", "verdict": "...", "evidence_quotes": ["..."], "rationale": "...",
     "contradiction_kind": null, "behavior_impact": null, "defect_key": null,
     "rule_basis": [], "hard_constraint_claim": null}
  ],
  "dimensions": [
    {"dimension": "correctness|flow|exceptions|acceptance|consistency",
     "anchor": 0, "evidence_quotes": ["..."],
     "defects": [{"description": "...", "quote": "...", "related_item": "R3|null"}]}
  ],
  "critical_candidates": [
    {"rule_id": "G3|P04-X1", "quote": "...", "rationale": "..."}
  ]
}
```

**约束（由程序校验，不满足则整份输出作废）：**
- 不得包含总分或任何汇总分字段（多余字段一律拒绝）。
- R、C 条目必须与用例清单一一对应，不多不少。
- 除 `missing` 外，每个判定至少一条 `evidence_quotes`；`missing` 判定的 `rationale` 需说明检查过哪些相关章节。
- `contradicted` 判定必须给出 `contradiction_kind`、`behavior_impact`、`defect_key`；`general` 还必须给出 `rule_basis`。非矛盾判定的这四个字段必须为空。
- 整个回复必须是一个 JSON 对象（允许包在一个 ```json 代码块中）；对象前后的文字、多个对象或数组一律作废。
- 每个维度锚点 < 4 时，必须至少列出一条 `defects`，说明为什么不是更高一档。
- 引用必须逐字摘自文档（允许空白字符差异，至少 4 个字符）；校验不通过的引用作废。一个判定的引用全部作废时，该判定记为"未核实"：需求覆盖率按 s=0 计，不触发上限和候选，转人工。
- 每份文档评两次，第二次打乱 R、C 条目顺序；两次判定不一致的条目全部转人工。两次的分数分别计算后取平均。

## 9. 人工复核

Pilot 阶段的复核范围：

1. 100% 的严重缺陷候选。
2. 100% 的 Judge 两次判定不一致的条目、引用校验失败的条目。
3. 随机抽取 ≥25% 的待评文档做全条目复核，按条件分层（A、B.best、B.v1 各占相同比例）。
4. Judge 与人工判定不一致时以人工为准，并记录不一致原因。

建议至少两名评审者独立复核第 3 项中的文档，报告两人一致率；分歧由第三人或讨论裁定，裁定记录保存在 `scores/<batch>/human/`。

## 10. 结果标注

- 每份文档的每个分数带 `provenance` 字段：`auto`（全部来自程序 + Judge）或 `human_reviewed`（至少经过第 9 节第 3 项的全条目复核）。只做了部分条目复核的，标 `partially_reviewed` 并列出复核过的条目。
- 报告中的汇总表分别给出"全部文档（含 auto）"和"仅 human_reviewed 文档"两套数字。
- Rubric 或金标准的任何修改都升版本号（如 `rubric-v0.5`），不同版本的分数不合并。
- 每份文档带 `status`：`pending`（有未裁定候选）或 `final`。有未裁定 G1 候选的文档 `final_total` 为空，报告列出基础评分、确认后、否决后三个情景；配对比较只使用有最终总分的文档。
- Rubric 修改后的分数不与旧版本合并；`rubric-v0.3` 及更早版本没有产生任何真实分数。
